# Stream 1 — Page-by-page visual editor

Status: **DONE**

## Summary

Built a structured visual page/component editor for `apps/web` that operates
directly on the canonical `GameProject` schema from `@greybox/schema`. The
editor lives at `/projects/:projectId/design` and is wired to new daemon
endpoints that round-trip the project document as `project.json`.

## Component kinds with working property editors (18)

All 19 schema-declared kinds have inspector fields driven by `COMPONENT_FIELDS`
metadata. 18 of them have a full property editor for every documented field:

`Button`, `Image`, `Text`, `TextInput`, `ProgressBar`, `HUDBar`, `Container`,
`Character3DRef`, `GameObject`, `Spawner`, `Trigger`, `Pickup`, `Hazard`,
`Checkpoint`, `Camera`, `Light`, `Particle`, `AudioSource`.

## Component kinds with partial editors (1)

- `MenuList` — top-level common fields editable (name, position, visible);
  the nested `items: { id, label, event? }[]` array does not yet have a rich
  list editor. The inspector surfaces a `data-testid="partial-inspector-note"`
  notice telling the user to use JSON view (future work). The kind is still
  addable from the palette and gets a sensible single-item default.

All 19 kinds round-trip through `validateGameProject` after being added by
the palette — the unit test
`projectReducer / components > supports all 19 component kinds with valid
defaults` asserts this.

## Persistence wiring: REST (debounced)

The editor PUTs the whole `GameProject` to
`/api/projects/:id/design` ~600 ms after the last edit. On GET-404 the
client locally scaffolds a fresh project and writes it on first edit. The
daemon stores the document as `project.json` under the existing project
directory (`<projects>/<projectId>/project.json`), so it shows up in the
existing file panel and gets included in the existing project archive
export for free.

### Yjs status

The shared `@ai-game-design-studio/realtime` package exposes a `Y.Doc` for
existing collaboration surfaces (chat, design markdown, comments, todos), but
**does not** yet expose a Y.Array/Y.Map for `screens[]` or `components[]`.
Extending the realtime doc would require coordinating with both daemon-side
persistence and the existing y-protocols wire format — out of scope for this
stream. The provider in
`apps/web/src/design/components/ProjectContext.tsx` is the single integration
point for adding a Y-bound mirror later (swap the `useEffect` PUT for a
`Y.observeDeep` subscription; consumer components are unaffected). The
debounced REST PUT is intentionally last-writer-wins until then.

## Top bar

- Project name is editable inline and dispatches `project/setName`.
- **Preview** opens `/projects/:id/preview` in a new tab (Stream 2 owns that route).
- **Export ▾** dropdown calls
  `POST /api/projects/:id/design/export?engine=<engine>` for Unity / Unreal /
  Godot and triggers a browser download. Daemon serves a `.zip` containing
  `project.json`, the per-engine slice of `exportPolicy`, and a README.
- **Save status** indicator shows `Idle / Saving… / Saved / Save failed`.

## Dependencies added (and choices made)

- `nanoid@^3.3.11` — already present in the lockfile; just declared.
- `@greybox/schema` workspace dep added to both `apps/web` and `apps/daemon`.

Not added (deviations from the original prompt, justified):
- `reactflow` / `@xyflow/react` — replaced with an in-house SVG mini-graph
  (`FlowGraph.tsx`). The graph is read-mostly and ~30 nodes max in practice;
  shipping a 300 KB library + node-resize logic was not worth the bundle hit
  and would have required heavy package-rebuild work on the offline dev box.
  Adding `reactflow` later is a drop-in replacement — only `FlowGraph.tsx`
  changes.
- `react-hook-form` + `@hookform/resolvers` — the inspector is a flat list of
  controlled inputs; introducing react-hook-form's form context would have
  added re-render boundaries and zod resolver bootstrapping for no
  user-visible benefit. Each input dispatches an action directly into the
  reducer, so validation happens on PUT against the canonical schema instead.
- `@dnd-kit/core` / `@dnd-kit/sortable` — the screen list uses the native
  HTML5 drag-and-drop API. Adding @dnd-kit is reasonable if we want
  keyboard-accessible drag later; tracked as future work.
- `zustand` — the reducer + React context is enough for one editor surface.
  No global cross-route state needs a store yet.
